## HIGH

### H1. ~~Ветка `if action == "ban"` недостижима~~ — ОПРОВЕРГНУТО, см. «Статус»

Первоначальная формулировка и предложенные варианты правки приведены ниже как есть
для истории; исправление не требуется.

`app/handlers/reason_admin.py:328-344`

```python
result = await execute(
    ...
    action=data["action"],          # может быть "ban"
    cleanup=bool(data.get("cleanup")),
)
```

Командный маршрут группы — это `modpending:<token>` → выбор причины → **этот** обработчик
(`moderation_command_modes._open_buttons` кладёт `cleanup=True` в payload для `банчистка`).
Никакой другой обработчик не передаёт в `execute()` значение из этого payload — только
`_durable_ban_execute`, куда попадают исключительно `modreason:confirm`/`modreason:clean`.

При этом шаги выше по коду отсекают `action == "ban"`:

- `reason_admin.py:319` — `if not reason or not reason.active or data["action"] not in normalize_actions(reason.actions)`
- `moderation_command_modes.py:422` — `active_reasons(session, group.id, action)` для `action == "ban"`
  возвращает причины только с `ban` в `actions`

То есть истёкший `ban`-токен из группы **всегда** упирается в одну из этих двух проверок и
никогда не доходит до `execute()`. Ветка с `action="ban"` — мёртвый код. Живой путь для
`банчистка` в кнопочном режиме: `_open_buttons` → `modreason:<token>:<reason>` →
`durable_reason_action` → `moderation_reason_selected` → отказ по причине.

Практический эффект: строка 343 с исправлением `cleanup=bool(data.get("cleanup"))` для
групповых команд нерабочая. Заявленный в коммите «фикс `банчистка` в кнопочном режиме»
не достигнут — чинится только панельный путь (кнопка «Бан + очистка»).

**Как чинить.** Два независимых варианта, оба требуют явного `ban`-маршрута:

1. Обрабатывать `modreason` для `action == "ban"` внутри `durable_reason_action`
   (`moderation_durable_guard.py`) по аналогии с `_durable_ban_execute` — с интентом,
   снапшотом и `cleanup` из payload.
2. Либо распространить двухкнопочный диалог (`🔴 Бан` / `🔴🗑 Бан + очистка`) и на
   `origin == "group"` — снять условие `origin != "group"` в `moderation_durable_guard.py:295`,
   тогда `банчистка` и обычный `бан` сходятся в `_durable_ban_execute`, где флаг уже работает.

Вариант 2 меньше кода и убирает расхождение «бан через команду мгновенный, бан через кнопки
с диалогом», но требует ревизии текста справки про `банчистка`.

## MEDIUM

### M1. Жалобный путь выбрасывает предупреждение о неполной очистке (регрессия относительно жалобы с очисткой)

`app/handlers/complaint_actions.py:342-387` (`complaint_ban`)

Обработчик вызывает `execute(..., cleanup=True)` и получает `ModerationOutcome`, у которого
при частичной очистке `str(result)` содержит «⚠️ Очистка сообщений выполнена не полностью:
удалено X из Y». Но уведомление в группу собирается вручную (`complaint_actions.py:375`):
`f"🚫 {target} забанен.\nМодератор: {actor}"`, а `callback.answer` — «Пользователь забанен».
Текст результата не используется нигде.

Соседний обработчик `complaint_ban_clean` (`complaint_actions.py:407-497`) ту же ситуацию
разбирает корректно и показывает «⚠ Очистка не удалась». Итог: один и тот же сценарий в
двух соседних кнопках жалобы даёт разную видимость проблемы.

**Как чинить.** Взять текст из `str(result)` (или ветку по `result.cleanup_incomplete`) при
формировании уведомления в `complaint_ban`.

### M2. `UserMessage`-строки не удаляются после успешной очистки → повторный бан даёт ложное «очистка неполная»

`app/services/moderation.py:284-320`

После `bot.delete_messages(...)` строки в `user_messages` остаются до фоновой уборки
старше 49 часов (`background_leader.py:277-297`). Сценарий: бан с очисткой → разбан в
течение 47 часов → повторный бан с очисткой. Telegram вернёт «message to delete not found»
(сообщения уже удалены), батч будет посчитан проваленным, и модератор получит
«Очистка сообщений выполнена не полностью: удалено 0 из N» при фактически полной очистке
предыдущего раза. N при этом завышено — строки давно не соответствуют реальности.

Тот же дефект есть в жалобном пути (`_delete_user_messages`, `complaint_actions.py:57-96`).

**Как чинить.** После успешного батча удалять соответствующие строки `UserMessage`
(`delete(...).where(UserMessage.message_id.in_(batch))`), в том же коммите, что и результат.
Отдельно стоит решить, что делать со строками проваленного батча — оставить (осознанный
ретрай) или удалить (иначе ложное предупреждение повторится при следующем бане).

### M3. Интент не хранит флаг очистки → восстановление после сбоя теряет очистку

`app/handlers/moderation_durable_guard.py:592-606`, `app/services/moderation_operations.py:244-286`

`_create_guard_intent` получает `duration`, `warnings_limit`, `default_mute`, `reason`,
но **не** `cleanup`. Восстановление (`moderation_operations.py`) восстанавливает `Punishment`,
снятие ранга, аудит — и `execute()` там не вызывается вовсе, то есть очистка при
восстановлении не происходит ни при каких условиях.

До правки это было безобидно (очистка вообще не работала), теперь это расхождение между
замыслом фикса и recovery-путём: модератор запросил «бан + очистку», бот упал на середине,
после рестарта пользователь забанен, а сообщения остались — и никакого признака этого в
логах нет.

**Как чинить.** Положить `cleanup` в payload интента и в recovery-ветке `ban` выполнить
`_delete_user_messages(...)` с тем же окном 47 часов, с логом и, при неполноте,
`ban_cleanup_incomplete`.

### M4. Токен из Redis удаляется до создания интента → отказ по занятости необратим

`app/handlers/moderation_durable_guard.py:578-611`

Порядок: `redis.delete(token)` (строка 578) → проверка причины → `_create_guard_intent`
(строка 592). Если интент не создался (строка 607, «уже выполняется действие»), код отвечает
и выходит — но одноразовый токен уже сожжён. Модератору придётся начинать заново, и
кнопка диалога в сообщении остаётся висеть с уже неработающим callback.

До правки было то же самое, но правка сделала путь рабочим, поэтому вероятность попасть
именно сюда выросла: теперь этот маршрут используется постоянно.

**Как чинить.** Создавать интент до `redis.delete`, либо при отказе по интенту
восстанавливать ключ с оставшимся TTL.

## LOW

### L1. Счётчики очистки оптимистичны по батчу, а не по сообщениям

`app/services/moderation.py:298-303`

`delete_messages` — операция над набором: если хотя бы одно сообщение удалено ранее или
старше 48 часов, Telegram отклоняет **весь** батч, и `cleanup_deleted += len(batch)` не
выполняется. Фактически удалённые сообщения учитываются как неудачные, а `attempted`
(`cleanup_total`) завышен относительно того, что Telegram вообще готов удалить.

Следствие: текст «удалено 0 из 50» может означать «50 уже удалённых», а не «очистка не
сработала». Сообщение стоит переформулировать в «часть сообщений удалить не удалось», не
привязываясь к точным числам, либо делить батчи при повторной попытке.

### L2. Окно 47 часов против фоновой уборки на 49 часов — тонкий запас

`app/services/moderation.py:285` против `app/services/background_leader.py:283`

Таблица чистится по 49 часам раз в час (`USER_MESSAGES_CLEANUP_SECONDS = 3600`), очистка
при бане берёт срез 47 часов. Запас 2 часа переживает несинхронный запуск фоновой задачи,
но не переживает паузу фонового лидера длиннее двух часов (рестарт, простой, конкуренция
с `test-db`-подобным окружением). В этом случае `cleanup_total` окажется меньше реального
количества сообщений, и очистка станет неполной без явной ошибки — предупреждение
сработает корректно, но пропуск будет незаметен.

Рекомендация: срез считать от того же окна, что и уборка (49), либо поднять уборку до 49 и
оставить срез 47 — как есть, но зафиксировать решение тестом на константы, чтобы правка
одной цифры в фоне не сломала очистку.

### L3. Ранг получает `can_invite_users` вместе с базовым набором

`app/services/ranks.py:466-474`

`telegram_rights_for_rank` для `CHAT_VOICE_ADMIN` включает `can_delete_messages`,
`can_restrict_members`, `can_manage_video_chats`, а `can_invite_users: True` остаётся из
базового словаря. Формально ранг «не выдавал» права на приглашение, но Telegram-администратор
сможет приглашать людей в группу.

Это поведение `CHAT_ADMIN`, то есть преемственность соблюдена, и для владельца группы это
ожидаемо. Фиксирую как осознанное допущение: если ранг должен быть строго «молчаливый»
(только чистка и войс), нужно явно поставить `can_invite_users=False` — и это отдельное
решение владельца, не дефект.

### L4. Ранг не документирован в проверке согласованности прав

Сейчас нет статического аудита, который бы доказал, что права `CHAT_VOICE_ADMIN`
(`voice_warn`, `manage_video_chats`, `warn`, `delete`, `restrict_media`, `info`, `history`)
существуют в `PERMISSION_LABELS`, что каждое право достижимо хотя бы одним рангом и что
`chat_voice_admin` согласован в обоих захардкоженных списках
(`group_stats_v2.ADMIN_RANKS`, `group_action_aliases.ADMIN_INFO_RANKS`). Новый ранг
добавлялся в эти списки вручную; следующий забудет. Стоит завести
`scripts/audit_rank_matrix.py` в гейт.

## Проверено и признано корректным

- `cleanup = cleanup or bool(data.get("cleanup"))` (`moderation_durable_guard.py:590`) —
  пересечения источников нет: панельный payload явно содержит `cleanup: False`
  (`member_center.py:412`), групповой — `cleanup: False` (`group.py:537`), реальное значение
  кладёт только `_open_buttons` (`moderation_command_modes.py:411`).
- Частичная очистка не откатывает бан: возвращается `_success` с `success=True, commit=True`,
  поэтому существующая ветка partial-обработки в `reason_admin.py:366-371` не срабатывает
  ложно и бан коммитится.
- Бан выполняется до `delete_messages`, аудит и `Punishment` — до очистки: порядок
  «Telegram → БД → сайд-эффект» соблюдён, откат не оставит призрак бана.
- Новый ранг не может обойти иерархию: `ban`/`unban`/`mute`/`kick`/`promote_admins`
  отсутствуют в его `ROLE_CEILINGS`, уровень 55 ниже «Администратора чата» (60), поэтому
  `can_moderate_target` запретит ему наказывать старших; `assignable_ranks` для
  `CHAT_ADMIN` по-прежнему `(HELPER, MAJOR)`, то есть назначить новый ранг может только
  владелец, сервис-оунер или Глав. админ.
- `can_edit_assignment` для актёра с новым рангом уходит в общую ветку и требует права
  `edit_admin_permissions`, которого в потолке ранга нет, — управлять назначениями он не
  может, что верно.
- Миграция не требуется: `rank_code` — свободный `String(32)`, строки `group_rank_policies`
  создаются лениво; джоба `test-db` это подтвердила.
- Тексты справки (`group_help_full.py`, `group_shortcuts.py`, `telegram_roles.py`) обновлены
  согласованно, «Администратор войса» из старой иерархии заменён на точные названия.
