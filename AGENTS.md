# Mimoru — правила разработки

## Главная копия

Источник истины проекта — ветка `main` публичного GitHub-репозитория:

`maksimnelson356-sudo/Mimoru`

Серверная копия:

`/root/Mimoru`

Сервер используется для реального тестирования Mimoru и получает код из GitHub. Не вносить постоянные исправления напрямую на сервере: сначала изменить и проверить код в GitHub, затем обновить сервер штатным деплоем.

SSH remote сервера для этого проекта настроен отдельно от других проектов через alias `github-mimoru`.

Штатное обновление сервера:

```bash
bash /root/Mimoru/scripts/deploy.sh
```


## Рабочий процесс

Для каждой задачи:

1. Изучи существующий код и архитектуру.
2. Составь краткий технический план.
3. Внеси изменения в GitHub.
4. Запусти/дождись CI и доступных автоматических проверок.
5. Если CI или аудит находит ошибку — исправь её и повторяй проверки до зелёного результата.
6. Для runtime-изменений попроси владельца выполнить `bash /root/Mimoru/scripts/deploy.sh` на сервере.
7. Проверь присланный вывод Docker Compose, Alembic, preflight, healthcheck и Telegram polling.
8. Для функций, которые невозможно достоверно проверить без Telegram/живых данных, дай конкретный сценарий ручной проверки на сервере.
9. Если обнаружена runtime-ошибка — исправь её в GitHub и повтори цикл GitHub CI → deploy → server check.
10. Не считать изменение полностью готовым к реальному использованию, пока обязательная runtime-проверка не пройдена.


## Проверки

В проекте два независимых гейта.

`./scripts/check.sh` — быстрый гейт без базы данных: компиляция, Ruff, pytest (без маркера `db`), все статические аудиты. Запускается где угодно, обязан быть зелёным всегда.

`./scripts/check_db.sh` — проверки, которые невозможно выполнить на моках: реальное применение всей цепочки миграций на пустой базе, `scripts.ensure_version_column`, `app.preflight`, сверка живой схемы с ORM, уникальные ограничения, защищающие от повторного списания, и поведение `FOR UPDATE` / `FOR UPDATE SKIP LOCKED`. Требует живого PostgreSQL, в CI выполняется на сервис-контейнере `postgres:17-alpine`. Скрипт никогда не пропускает проверки молча — без базы он падает.

Тесты с маркером `db` не должны попадать в быстрый гейт, а джоба `test-db` в CI не должна удаляться без замены проверки.

Если нет локального Docker или PostgreSQL, изменения схемы, миграций и конкурентной логики нельзя считать проверенными, пока не пройдена джоба `test-db` в CI.


## Серверная проверка

Используй при необходимости:

```bash
docker compose config
docker compose up -d --build
docker compose ps
docker compose logs --tail=200 bot
```

Проверяй:

- bot работает и не перезапускается;
- bot healthy;
- PostgreSQL healthy;
- Redis healthy;
- Alembic migrations проходят;
- preflight проходит;
- Telegram polling работает;
- отсутствуют новые критические ERROR, Exception и Traceback.


## Безопасность

Никогда не раскрывай:

- BOT_TOKEN;
- пароли;
- API-ключи;
- приватные SSH-ключи;
- содержимое серверного `.env`;
- другие секреты.

Никогда не перезаписывай:

`/root/Mimoru/.env`

Не выполняй без явного разрешения пользователя:

```bash
docker compose down -v
docker volume rm
DROP DATABASE
```

Не удаляй PostgreSQL/Redis volumes, backups или пользовательские данные.

Не трогай Solvira, AnonBot и другие проекты, контейнеры, базы данных, SSH-ключи и Redis на сервере.

Работай только с Mimoru.


## Git и деплой

- Основная рабочая ветка — `main`.
- Сервер должен получать изменения через `git pull --ff-only` внутри штатного `scripts/deploy.sh`.
- Не делать force-push `main` без исключительной причины и явного согласования.
- Не коммитить `.env`, ключи, токены, пароли, дампы базы или другие секреты.
- Для рискованных или крупных изменений предпочтительна отдельная ветка/PR; небольшие исправления допустимы напрямую при обязательном зелёном CI.
- Публичный репозиторий не должен выполнять PR-код на self-hosted runner с доступом к серверу или секретам.


## База данных

Не удаляй и не переименовывай существующие Alembic migrations без серьёзной технической причины.

Не ломай историю миграций.

Для новых изменений схемы создавай новую миграцию.

В проекте уже исправлена проблема `alembic_version.version_num` для длинных revision ID через `VARCHAR(255)`.

Не отменяй это исправление без технической причины.


## Навигация и формы

Для всех пользовательских экранов действует единый контракт:

- `Назад` возвращает на логически предыдущий экран, а не просто в главное меню;
- экран, доступный из нескольких мест, должен сохранять или явно передавать контекст родителя;
- `Отменить ввод` очищает активное FSM-состояние до перехода назад;
- после отмены следующий текст пользователя не должен попадать в отменённую форму;
- после успешного ввода пользователь возвращается к логической карточке/списку/редактору;
- старые callback-кнопки из истории Telegram должны либо работать, либо безопасно перенаправляться на актуальный экран.

При изменениях навигации обновляй автоматические проверки и регрессионные тесты.


## Разработка

Не выполняй массовый рефакторинг без необходимости.

Сохраняй существующую функциональность Mimoru.

При добавлении функций добавляй или обновляй тесты, когда это уместно.

Ошибки, появившиеся из-за текущих изменений, исправляй самостоятельно и повторяй проверки.

Если требуется опасная операция, удаление данных, изменение секретов или вмешательство в другие проекты — остановись и сначала запроси разрешение пользователя.


## Критерий готовности

Не считай задачу выполненной только потому, что код написан.

Автоматический цикл:

`GITHUB -> CI -> FIX -> CI`

Для runtime-изменений:

`GITHUB -> CI -> SERVER DEPLOY -> HEALTH/LOGS -> LIVE TEST -> FIX -> REPEAT`


## Финальный отчёт

После существенной задачи сообщи:

1. Что сделано.
2. Какие файлы изменены.
3. Какие автоматические тесты и аудиты выполнены.
4. Какие ошибки обнаружены.
5. Какие ошибки исправлены.
6. Результат серверной проверки, если она требовалась и была выполнена пользователем.
7. Статус bot/postgres/redis при runtime-проверке.
8. Есть ли новые критические ошибки в логах.
9. Затронуты ли другие проекты.
10. Совпадает ли серверный код с `main` после деплоя.
11. Готово ли изменение к реальному использованию или какие live-проверки ещё остаются.
